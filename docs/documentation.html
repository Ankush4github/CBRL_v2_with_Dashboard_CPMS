Part I

Content Editor's Guide

Everything you need in order to keep the CBRL website up to date — adding a new lab member, recording a publication, publishing photographs from a conference — without touching any code.

Who this part is for Anyone whose Google account has been granted editor access: research scholars, staff, or the PI. No programming knowledge is assumed. You will need a web browser, the address of the site, and that Google account.

1What the dashboard controls

The dashboard lives at /admin on the website — for the live site that is https://cbrl.iitkgp.ac.in/admin. It edits the parts of the site that change often, and it publishes instantly: there is no separate "deploy" step and no waiting for a developer.

Dashboard sectionPublic pageWhat you can change
Overview—A summary of what is currently on the site. Nothing is edited here.
Home page/The background images behind the homepage banner, and the collaborator logos.
Members/membersFaculty, postdoctoral fellows, research scholars, staff and alumni — including photographs and profile links.
About the PI/about-the-piThe PI's banner, portrait and profile, headline figures, biography, awards, research impact and office address.
Publications/publicationsThe list of peer-reviewed papers. Add by DOI, paste BibTeX, or fill in a form.
Projects/projectsOngoing funded projects, their objectives, the completed-projects PDF, and sponsor logos.
Research areas/researchThe research areas and the disease topics written up under each.
Gallery/galleryPhoto albums, their categories, cover images and captions.
Facilities/facilitiesInstruments, their features and in-charges, headline figures, and slot charges.
Citation metrics/publicationsTotal citations, h-index, and the source link shown alongside the publication list.
Everything else

Page wording outside these sections — the homepage text, the contact details in the footer — is part of the site's code and needs a developer. If you are unsure whether something is editable, look for it in the sidebar; if it is not there, it is not editable from the dashboard.

2Signing in

  1. Go to https://cbrl.iitkgp.ac.in/admin in any modern browser.
  2. Press Continue with Google and choose the Google account that has been granted editor access. There is no dashboard password.
  3. Google sends you back to the site and you arrive at the Overview screen. If you were trying to reach a particular section before signing in, you are returned to it automatically.

Access is granted per account, by your administrator. Being able to sign in to Google is not enough on its own: the account must also be on the list of website editors.

If you see "That account is not a website editor"

Google signed you in, but that account has not been given editor access. Check that you chose the right Google account. If you did, ask your administrator to grant it access (section 12.1 for them), then sign in again. If you also use the lab's patient system (CPMS) with the same account, this refusal does not sign you out of it.

If you see "Sign-in did not complete"

The round trip through Google was interrupted or cancelled. Press Continue with Google again.

If you see "The dashboard is not configured yet"

The server has not been set up for sign-in. This is not something you can fix from the browser — contact your system administrator and point them at section 10 of this document.

Every change is attributable

Because everyone signs in with their own account, the site records which account made each save. Never sign in on someone else's behalf, and tell your administrator when somebody with access leaves the group so their access can be withdrawn.

3Sessions and the inactivity timeout

Being signed in does not last indefinitely. Two separate limits apply, and whichever is reached first signs you out.

LimitDurationBehaviour
Inactivity timeout 5 minutes Five minutes with no typing, clicking, scrolling or mouse movement ends the session. Any activity resets the clock.
Absolute session length 8 hours Eight hours after signing in the session ends regardless of how busy you have been. Sign in again to continue.

3.1The warning

One minute before the inactivity timeout expires, a panel appears in the middle of the screen titled "Still there?" with a countdown. You have three choices:

  • Stay signed in — dismisses the warning and resets the five minutes.
  • Sign out — ends the session immediately.
  • Do nothing — the countdown reaches zero and you are returned to the sign-in screen, which explains that you were signed out for inactivity.

Simply moving the mouse or pressing a key also dismisses the warning, because that counts as activity.

Unsaved work is lost

Being signed out discards anything you have typed but not saved. The warning exists to give you a minute to press Save changes first — treat it as a prompt to save, not as a notice you can ignore. If you are interrupted mid-edit, save before you walk away.

3.2Why five minutes, and what counts as activity

The timeout is deliberately short because the dashboard can change the public website. Typing counts as activity even though nothing is being sent to the server while you write, so composing a long paragraph will not sign you out. Activity in one browser tab keeps every other dashboard tab signed in as well.

If five minutes proves too disruptive for the way your group works, the limit is a server setting and your administrator can raise it — see section 10.

4How every editor screen works

The editable sections share the same layout and the same controls. Learn them once and every screen behaves the same way. (Publications is the one variation: it saves one entry at a time — see section 5.3.)

4.1The sidebar and the save bar

The sidebar on the left lists every section. On a narrow screen or a phone it is hidden behind the menu button at the top left.

The save bar is pinned to the bottom of the screen and is the only place work is committed. It always tells you the current state:

What it saysWhat it means
No changes yetNothing has been touched since the page loaded.
Unsaved changesYou have edited something. It exists only in your browser.
Saving…The change is being written to the site's database.
Saved — the live page is updatedDone. The public page already reflects it.
Last saved 5 minutes agoEverything is saved; this is when it happened.

The View page button at the top right of each section opens the public page it drives in a new tab, so you can check a change immediately after saving.

4.2Adding, reordering and removing entries

Lists — members, projects, albums, instruments — are shown as collapsed cards, numbered, with the title on the left. Click a card to expand it and edit its fields; click again to collapse.

ControlEffect
Add buttonAppends a new blank entry at the end of the list. Expand it and fill it in.
▲ / ▼ arrowsMove the entry one place up or down. This order is exactly the order visitors see. The arrows grey out at the ends of the list.
Bin iconRemoves the entry — click once to arm it, and the row turns red asking you to confirm; click the bin a second time to remove it. Clicking anywhere else cancels.
Nothing is permanent until you save

Adding, reordering and removing all happen in your browser only. Nothing reaches the website until you press Save changes — and until then, Discard changes puts everything back exactly as it was.

4.3Saving, discarding and validation errors

Press Save changes to publish. The server checks the whole document before writing anything. If something is wrong, nothing is saved and the save bar lists the problems, each naming the exact field, for example:

students[4].email  must be a valid email address
albums[2].image    is required

Read this as: the fifth research scholar has a malformed email address, and the third gallery album has no cover image. Counting starts at zero, so [4] is the fifth entry. Fix the named fields and save again. At most twelve problems are listed at once; if there are more, the list ends with a count of the remainder.

Discard changes throws away everything unsaved and reloads what is currently published. It cannot be undone, but it also cannot affect the live site.

What the server tidies up for you

Saving normalises the document: spaces at the beginning and end of fields are trimmed, blank rows in lists are dropped, and duplicated identifiers are made unique. The form redraws to show exactly what was stored, so if a field looks slightly different after saving, that is why.

4.4Uploading images

Anywhere the site shows a photograph you get an image box: a small preview, the current image path, and an Upload image button (Replace image once one is set).

  1. Click Upload image and choose a file. JPEG, PNG, WebP, AVIF and GIF are accepted, up to 12 MB.
  2. The server converts it to WebP, rotates it upright, resizes it to a sensible width for where it will appear, and stores it in the site's image store. The image's address fills in automatically — a full https://…/site-media/… address.
  3. Press Save changes. The upload alone does not publish anything.

Clear removes the image from the entry. It does not delete the uploaded file from the image store.

Why replaced photos appear instantly

Every upload is given a filename containing a fingerprint of its contents, so a replacement always arrives at a brand-new address. That is why you never have to clear your browser cache to see an updated photograph.

You may also type a path directly into the box — useful for one of the older images that ship with the site itself. It must begin with / and point inside the site, for example /images/MembersDP/ankush-das.webp. Other full web addresses beginning http:// or https:// are rejected; the only ones accepted are the addresses of images uploaded from the dashboard.

5Section by section

5.1Overview

The landing screen after signing in. It reports how many members, publications, projects, albums and instruments are currently published, gives a one-line count for every section, and links to each. Nothing is editable here — it is a place to confirm the site holds what you expect.

Renaming a member breaks their link

Each member has a hidden identifier derived from their name the first time they are saved, and the public site links to individual cards using it — /members#ankush-das. Changing a spelling is fine, but be aware that any link shared earlier to that specific card may stop working. If two members would end up with the same identifier, the second is automatically given a numbered suffix.

Moving somebody to Alumni

There is no automatic transfer. Remove the person from their current group, add them under Alumni, and re-enter their details — adding Current position and Thesis title, which only Alumni displays. Do it in a single sitting and save once.

5.3Publications

The publications page is generated from a BibTeX record of roughly 180 entries. The editor works on one entry at a time — every other entry in the record is left untouched, byte for byte — so there is no risk of a stray edit disturbing the rest of the list. Each add, edit or delete is saved on its own as soon as you confirm it, rather than through the save bar.

Three ways to add a paper

MethodHow it works
By DOI
recommended		 Paste the DOI — 10.1016/j.bios.2026.118980, or the full https://doi.org/… address — and the server fetches the full record from doi.org. Check the filled-in fields and save.
Paste BibTeX Paste an entry copied from the publisher or Google Scholar. It must start with @article{ or similar. Several entries can be pasted at once and they keep their order.
Fill the form Type the title, authors, journal, year and so on by hand. Use this when a paper has no DOI yet.

New entries are added at the top of the record. The public page groups everything by year regardless, so position within the record does not affect what visitors see.

Editing and deleting

Existing entries are listed with their title, authors and year. Open one to edit its fields, or delete it outright. Fields the public page does not display — keywords, issn, abstract — are preserved even though the form does not show them.

Duplicate citation keys

Every entry carries a citation key, which must be unique. If a paste or a DOI import produces a key already in use, the entry is flagged as a duplicate. Give one of them a slightly different key — appending a or the journal abbreviation is the usual fix.

If a DOI lookup fails

MessageWhat to do
"That does not look like a DOI"The DOI must start 10. followed by four or more digits, a slash, then the suffix. Remove any surrounding text.
"No record found for that DOI"The DOI is not registered. Check it against the publisher's page; very new papers sometimes take days to appear.
"Could not reach doi.org"The server has no internet access, or doi.org is down. Paste the BibTeX instead — that does not need doi.org.

5.4Projects

Three separate things live here.

Ongoing projects

Each card carries a title and a short description (both required), plus duration, funding agency, your role, a detailed description, methodology and expected outcomes. Objectives is a list — add one line per objective; blank lines are dropped when you save. The icon is a single emoji shown beside the title and defaults to 🔬 if left empty.

Completed projects PDF

A single link to the PDF listing finished projects. It must be a path inside the site beginning /, such as /data/completed-projects.pdf. Replacing the document is a job for your administrator — the dashboard uploads images only, not PDFs.

Sponsor logos

Each sponsor needs an image, descriptive alt text for screen readers, and its width and height in pixels. All four are required. The dimensions stop the page jumping about while logos load, so they must match the real image — your image viewer or the file's properties will tell you.

5.5Research areas

A two-level structure. Each area has a number badge, a title, a tagline and a description. Inside it sit topics, shown on the public page as an expanding accordion.

Each topic has a title, a one-line summary, and a body made of separate paragraphs — add one box per paragraph rather than pressing Enter inside a single box, which is what produces the spacing on the published page.

The index badge (01, 02, …) is filled in automatically from the position of the area if you leave it blank, so reordering areas renumbers them.

5.6Gallery

Categories are defined first, as a simple list — "Conferences", "Awards", "Lab outings". Every album must then be given a category from that list; a category that is not in the list is rejected when you save.

Each album needs a title and a cover image (both required), and may also carry a caption, a date, a longer description and any number of additional photographs. Gallery uploads may be filed into a sub-folder, which keeps large albums tidy in the image store.

Removing a category

Deleting a category from the list while albums still use it makes those albums fail to save, with an error naming the allowed categories. Move the albums to another category first, then remove the old one.

5.7Facilities

Three groups of content:

  • Headline figures — the short statistics across the top of the page. Each is a value (up to 20 characters, e.g. "12+") and a label (up to 40 characters, e.g. "Major instruments"). Both required.
  • Instruments — title, photograph and its alt text are all required. Each may also list features, a funding source, and an in-charge with name, title, email and a profile link.
  • Slot charges — each charge block has a title, a duration, and a list of price rows (label and value, both required, such as "IIT KGP internal" / "₹500"). The note below the table is edited in Charges note.

5.8Citation metrics

The small panel of figures on the publications page. Four fields, all required:

FieldNotes
Total citationsFree text, so "4,250" and "4250+" are both fine. Up to 20 characters.
h-indexA whole number between 0 and 500.
Source nameUsually "Google Scholar".
Source URLMust start https://.
Last updatedMust be written YYYY-MM-DD — for example 2026-07-27.

These figures are typed in by hand; nothing fetches them automatically. Refreshing them once a term is a sensible habit.

5.9Home page

Two lists:

  • Background images — the photographs behind the homepage banner. Each needs an image and alt text (up to 200 characters) describing it for screen readers. At least one image is required. Uploads are resized to 2400 px wide; landscape photographs work best, because the banner crops to fill.
  • Collaborators — each logo needs a name (the caption under the logo), the logo image and its alt text. An optional Website turns the card into a link. You also choose the Row it sits in (1 or 2), a Display width between 20 and 400 px, and the file's source width and height in pixels — these are filled in for you when you upload the logo.
SVG logos

SVG files cannot be uploaded. An SVG logo has to be placed in public/images/Collab/ by your administrator, after which you type its path into the logo box.

5.10About the PI

One page, edited in blocks:

BlockWhat it holds

ProfilePortrait and its description, name and email (all required), plus position, institution and phone. The portrait is cropped to 4:5, so keep the face towards the top.
Headline figuresValue and label pairs beside the portrait, both required. Type {publications} as a value to show the live publication count.

7When something goes wrong

What you seeWhat it means and what to do
"Some fields need attention before this can be saved." Validation failed and nothing was written. Each listed line names the field. Fix them and save again — see section 4.3.
"Could not save your changes. If this keeps happening, the signed-in account may no longer be a site editor." The database refused or did not receive the save. Nothing was lost from your screen — do not reload. Try once more; if it fails again, copy your work somewhere safe and contact your administrator (section 20 for them). The usual cause is that your editor access has been withdrawn.
"This section could not be loaded" The site's database could not be read, so the editor was deliberately not opened — editing an out-of-date copy would overwrite recent changes. Nothing has been changed. Press Try again after a moment. The same cause can show as "Could not load … from the database. Nothing was changed — try again in a moment."
"Could not reach the server." Your network connection dropped, or the site is down. Your edits are still on screen. Restore the connection and press Save again.
Sent back to the sign-in page unexpectedly The session expired — five minutes idle or eight hours total. Sign in again. Unsaved work is gone; see section 3.
"You were signed out after a period of inactivity." Confirmation of the five-minute timeout. Sign in and continue.
"That account is not a website editor." The Google account you chose has no editor access, or its access has been withdrawn. Check you picked the right account; otherwise ask your administrator — see section 2.
"Could not store the image." The upload was converted but could not be saved to the image store. Try again; if it persists, the likely cause is that your editor access has been withdrawn.
"The dashboard is not available from your network." An address restriction is in force and yours is not on the list. Try from the campus network, or ask your administrator — section 13.
"This request did not come from the dashboard." Usually a stale browser tab left open a long time. Reload the page and try again.
"That image is larger than 12 MB." Resize or compress the photograph before uploading. Anything much above 2,000 pixels wide is larger than the site needs.
"That file could not be read as an image." The file is corrupt, or it is not really an image — a PDF renamed .jpg, for instance. Re-export it and try again.
A saved change is not visible on the public page Confirm the save bar said "Saved". Then reload the public page with Ctrl+F5. If it is still missing, tell your administrator which section and field.
Reporting a problem usefully

Include the section you were editing, the exact wording of the message, roughly when it happened, and whether you had just uploaded an image. The server keeps logs, and a timestamp makes the matching entry easy to find.

Part II

System Administrator's Guide

Installing, configuring, securing, deploying and maintaining the application — including the authentication model, the reverse-proxy requirements it depends on, and the runbook for when something breaks.

Who this part is for Whoever operates the server. Assumes a working knowledge of the command line, Node.js, nginx and the Supabase dashboard. Read sections 12 to 14 before exposing the dashboard to a network.

8Architecture

LayerTechnology
FrameworkNext.js 16 (App Router, Turbopack)
LanguageTypeScript 5, target ES2017
UIReact 19, Tailwind CSS 3, Radix primitives
ImagesNext.js Image, Sharp for upload re-encoding
Contact formEmailJS, entirely client-side
Content storeSupabase Postgres — table public.site_content, one row per collection, with every previous version kept in public.site_content_versions
Image storeSupabase Storage — public bucket site-media, WebP only
AuthGoogle sign-in through Supabase Auth, a per-account grant in public.site_editors, and an HMAC-SHA256 signed activity cookie (Web Crypto) for the idle timeout and absolute cap

The Supabase project is the one shared with CPMS, the lab's patient system, which runs in the same Next.js application under /cpms. The application holds only the project's publishable key. There is no service-role key anywhere in the app: row-level security is what keeps website editors away from patient records, and a service-role key would bypass it.

The files under content/ and public/data/ are not what the dashboard edits. They are the seed the database was first filled from (section 9.4, migrate:content) and a last-resort fallback for the public site when the database cannot be read — see section 11.

One gate, no per-route checks

src/proxy.ts runs ahead of every /admin page and /api/admin endpoint. Address allowlist, Origin check, Supabase sign-in with its site_editors grant, and the activity cookie all live there, which is why no individual route can ship without them. Read it first when auditing. It is the gate, not the authorisation: writes are authorised again by the database itself (section 13).

9Installation and the build

9.1Requirements

  • Node.js 20.9 or newer — required by Next.js 16.
  • npm (a package-lock.json is committed).
  • A build host able to compile Sharp, or one of its prebuilt binaries.
  • Access to the Supabase project, with Google enabled as a sign-in provider under Authentication, and https://<your-host>/admin/auth/callback registered under Authentication → URL Configuration — otherwise Google answers with a redirect mismatch.
  • Outbound HTTPS from the server to the Supabase project, and to doi.org for DOI imports.

9.2First run

git clone https://github.com/Ankush4github/CBRL_v2_with_Dashboard_CPMS.git
cd CBRL_v2_with_Dashboard_CPMS
npm install

cp .env.example .env.local     # then edit it — see section 10
npm run dev                    # http://localhost:3200

On a brand-new Supabase project, apply the migrations in supabase/migrations/ and seed the content once with npm run migrate:content (section 9.4). Then grant yourself editor access (section 12.1).

9.3Production

npm run build                  # clears Next's persisted fetch cache, then builds
npm start                      # serves the build on port 3200

It is the only thing in the repository that uses the Supabase service-role key, because there is no editor to sign in as before the first grant exists. Pass the key for that one command only — never put it in .env.local, where the app would pick it up:

SUPABASE_SERVICE_ROLE_KEY=<key> npm run migrate:content            # bash
$env:SUPABASE_SERVICE_ROLE_KEY = "<key>"; npm run migrate:content   # PowerShell

Once editors have started saving, a full run rolls every collection back to its last committed copy (recoverable from site_content_versions, but not something to do by accident). To seed a single newly added collection, name it: npm run migrate:content -- about.

10Environment variables

All configuration lives in .env.local, which is gitignored. Restart the server after any change. .env.example is the annotated template.

10.1Required for the dashboard

VariablePurpose
NEXT_PUBLIC_SUPABASE_URL The Supabase project URL, https://<ref>.supabase.co. The same project backs the dashboard and CPMS.
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY The project's publishable key. It is visible in the browser bundle by design; an anonymous holder can read the public website content and nothing more. Never add a service-role key to the app's environment.
ADMIN_SESSION_SECRET Signs the activity cookie that enforces the idle timeout and the 8-hour cap. Minimum 16 characters; below that the dashboard counts as unconfigured. Changing it signs every editor out of the dashboard immediately.

There is no dashboard password variable. Who may edit is decided per account by public.site_editors (section 12.1), not by configuration.

Generate a secret with:

node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
If these are unset

Raising the idle timeout

Five minutes is short by design, but the editors hold unsaved drafts in the browser. If your editors write long-form content and complain about losing work, raising this to 15 or 30 minutes is reasonable — a timeout people work around is worse than a longer one they respect.

11How content is stored and revalidated

Content lives in the Supabase database, not on the server's disk. The public pages are statically generated from it, and a dashboard save drops the cached render of the pages that depend on what changed — so the change is live on the next request, with no rebuild and no redeploy.

11.1Where each thing lives

WhatWhere
Each JSON collectionOne row in public.site_content, keyed by collection (home, members, projects, research, gallery, facilities, about, metrics), document in the data jsonb column.
PublicationsThe row publications, stored as BibTeX text in the raw column so it survives byte for byte.
Who saved last, and whensite_content.updated_by (the editor's Supabase user id) and updated_at, stamped by the database.
Every previous versionpublic.site_content_versions — see section 18.
Uploaded imagesThe public Supabase Storage bucket site-media — section 11.5.

11.2The write path

  1. Validate. The whole document is checked and normalised. A single bad field rejects the entire save with a 422 and a per-field issue list; nothing is written.
  2. Write as the editor. The row is upserted through the editor's own Supabase session. The row-level security policy on site_content re-checks is_site_editor() for that account, so the database — not the proxy — is what authorises the write.
  3. Snapshot. A BEFORE UPDATE trigger copies the row as it was into site_content_versions and stamps the new row's updated_at and updated_by.
  4. Revalidate. revalidatePath() drops the cached render of the pages that depend on the collection.

11.3Reads, and the committed fallback copy

The public pages read site_content with the publishable key and no session — the table is world-readable because the site it renders is public. If a collection has no row yet, or the database cannot be read, the public site falls back to the committed copy on disk (content/<collection>.json, public/data/metrics.json, public/data/publications.bib) and logs a [content] warning. That copy is only as fresh as the last commit, so a page rendered from it may be showing content the dashboard has since changed.

The dashboard never falls back

An editor seeded from the disk copy would save the whole document back and silently replace every edit made since that commit. So when the database read fails, each editor page shows "This section could not be loaded" instead of opening, and the admin API answers 503 with Retry-After: 5. The only case in which an editor opens on the disk copy is a collection that has never had a row, where there is nothing newer to lose.

11.5Uploads

Uploaded bytes are re-encoded through Sharp to WebP at quality 82 and given a content-hashed filename, then stored in the site-media bucket through the editor's own session, so the bucket's policies re-check the site_editors grant. 12Authentication and session model

Two independent things must both be true for a dashboard request to get through: Supabase says who you are and site_editors says you may edit, and a signed activity cookie says you have been here recently. Neither alone is enough.

12.1Google sign-in and the editor grant

  1. The sign-in page starts Supabase's Google OAuth flow, with /admin/auth/callback as the return address (carrying next= so a deep link survives the round trip; only paths under /admin are honoured).
  2. Google returns to /admin/auth/callback, which exchanges the one-time code for a Supabase session and fetches the user.
  3. It checks for a row in public.site_editors for that user with is_enabled = true. Without one it redirects to /admin/login?reason=denied. The Supabase session is deliberately left in place: the project is shared with CPMS, and signing the account out here would sign a clinician out of the patient system too.
  4. With a grant, it issues the activity cookie (section 12.2) and redirects to the requested page. A failed exchange redirects to /admin/login?reason=failed; an unconfigured dashboard redirects to the sign-in page, which says what is missing.

The proxy repeats the check on every request: supabase.auth.getUser(), which validates the session against the auth server rather than trusting the cookie, then the site_editors lookup. Both fail closed — if Supabase cannot be reached, the request is refused. Revoking a grant therefore takes effect on the editor's next request, whatever their cookies say.

Granting and withdrawing access

Grants are managed in the Supabase dashboard, not from the website. The account must exist in auth.users first; the simplest way is to have the person press Continue with Google once — they will be turned away as not an editor, but the account then exists (assuming the project allows new sign-ups). Then, in the SQL editor:

-- grant
insert into public.site_editors (user_id, note)
select id, 'Name — reason for access' from auth.users
 where email = 'person@example.org';

-- suspend without losing the record
update public.site_editors set is_enabled = false
 where user_id = (select id from auth.users where email = 'person@example.org');

From inside the application, row-level security lets an account read only its own site_editors row; managing other people's rows is restricted to master accounts.

12.2The activity cookie

Supabase refreshes its token indefinitely, so on its own a session left open on an unattended machine never ends. The activity cookie supplies what Supabase does not: a real idle timeout and an absolute cap. It is an HMAC-SHA256 signed token, keyed with ADMIN_SESSION_SECRET. Signing uses Web Crypto rather than node:crypto, so identical code verifies the cookie in the Edge-runtime proxy and inside Node route handlers.

PropertyValue
Name (production)__Host-cbrl_admin_session
Name (development)cbrl_admin_session
FlagshttpOnly, SameSite=Lax, Secure in production, Path=/
Max-AgeThe idle timeout (never past the absolute expiry), re-issued on every authenticated request

The __Host- prefix binds the cookie to the exact host: the browser accepts it only with Secure, Path=/ and no Domain, so no sibling *.iitkgp.ac.in site can set or shadow it. The prefix is dropped in development because a __Host- cookie without Secure is refused outright and npm run dev serves plain HTTP.

The cookie carries no secret of its own and no identity — only two timestamps and a signature over them. A stolen cookie is useless without the matching Supabase session, it expires on its own, and rotating ADMIN_SESSION_SECRET invalidates every one at once.

12.3Absolute expiry and idle timeout

The signed payload holds two clocks, and the session dies to whichever fires first:

FieldMeaningBehaviour
exp Absolute expiry Fixed at sign-in, 8 hours out, and never moved. No amount of activity extends a session beyond it.
seen Last activity Slid forward by the proxy on every authenticated request. Once it falls further behind than the idle timeout, the session is over.

Keeping seen inside the signed payload is what makes the idle timeout real rather than decorative: the browser cannot move it, so a client that never runs the in-page timer is still signed out by the server. The Max-Age on the cookie is set to the idle timeout as a second line of defence — a browser closed for longer than that has nothing left to send.

The proxy tells the cases apart. Page requests are redirected to /admin/login (preserving the page they were on via next=) with reason=timeout for an idle session or reason=denied for an account without a grant. API requests receive 401 with {"reason":"timeout"} or {"reason":"unauthenticated"}, or 403 with {"reason":"forbidden"} for a non-editor. All of these clear the activity cookie; none of them signs the account out of Supabase. The dashboard's Sign out button does both, through /api/admin/logout, using a local-scope Supabase sign-out so the account's sessions elsewhere are not revoked.

12.4The activity heartbeat

The editors keep drafts in the browser and only contact the server on save, so somebody typing a long abstract generates no requests for minutes — indistinguishable, to a request-counting timeout, from an empty chair. src/components/admin/SessionTimeout.tsx closes that gap:

  • Pointer, keyboard, wheel, scroll and touch events count as activity, recorded at most once a second.
  • When activity has occurred, a POST /api/admin/heartbeat slides the server-side clock, at most about once every quarter of the idle timeout.
  • A warning panel appears 60 seconds before expiry; reaching zero signs the user out.
  • Activity is shared between tabs through localStorage, so work in one tab keeps the others alive.
  • Everything is measured against wall-clock time rather than counted down, so a slept laptop or a throttled background tab still reaches the right conclusion on its next tick.
The heartbeat cannot keep an idle session alive

It fires only when genuine interaction has been recorded since the previous one. An untouched tab sends nothing and times out normally. It is also a POST, so the Origin check applies and no other site can trigger it.

13Security layers

Sign-in decides who reaches the dashboard; the database decides what they may change. The layers, outermost first:

LayerWhat it does
IP allowlist Optional ADMIN_ALLOWED_IPS, applied ahead of everything else, including the sign-in page and the OAuth callback. With the allowlist on, an address that cannot be established is refused. An allowlist consisting only of unparseable entries is treated as unset, so a typo cannot lock everybody out permanently.
Origin check Every non-GET request to /api/admin/* must carry an Origin matching the site. SameSite=Lax alone is insufficient here because it treats every *.iitkgp.ac.in host as same-site, so a compromised neighbour could otherwise drive authenticated writes.
Sign-in and grant A Supabase session validated with getUser() on every request, plus an enabled site_editors row. Both fail closed.
Activity cookie HMAC-SHA256 signed, httpOnly, Secure, 8-hour absolute cap and 5-minute idle timeout. Host-bound by the __Host- prefix.
Row-level security The real authorisation. Inserts and updates on site_content, and writes to the site-media bucket, require is_site_editor(auth.uid()) for the editor's own JWT. site_content has no delete policy. site_content_versions is readable by editors only and written only by the trigger. The app holds the publishable key only, so a flaw in the app yields no more than an anonymous visitor already has.
Upload hardening Re-encoded through Sharp to .webp; the declared type and filename are never trusted. Destinations are chosen from a fixed set of folders in the bucket, and the bucket accepts image/webp only, up to 12 MB.
Write safety Validated before writing; editors refuse to open when the database cannot be read, so a stale copy is never saved over live content; every update is snapshotted into site_content_versions.
Path validation Saved asset paths must be a site path beginning with a single /, or begin with the project's site-media public URL; .. is rejected in both. No record can point the site's images at another origin.
Response headers A strict CSP, HSTS, X-Frame-Options: DENY, nosniff, a Referrer-Policy and a restrictive Permissions-Policy are set site-wide in next.config.js. The proxy additionally marks every /admin and /api/admin response no-store.
Scripting against the API

The Origin check rejects non-browser clients such as curl, which never send that header. Pass -H "Origin: https://cbrl.iitkgp.ac.in" when scripting writes.

14Reverse proxy configuration

The IP allowlist depends on nginx replacing or appending to X-Forwarded-For rather than passing the caller's value through untouched. Next.js 16 exposes no socket address in either runtime, so this header is the only source of a client address. The Origin check depends on X-Forwarded-Proto and X-Forwarded-Host, unless ADMIN_ORIGIN is pinned.

location / {
    proxy_pass         http://127.0.0.1:3200;
    proxy_http_version 1.1;

    proxy_set_header   Host              $host;
    proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header   X-Forwarded-Proto $scheme;
    proxy_set_header   X-Forwarded-Host  $host;

    proxy_set_header   Upgrade    $http_upgrade;
    proxy_set_header   Connection "upgrade";
}

$proxy_add_x_forwarded_for is the important one: it appends the peer nginx actually spoke to, which is what makes the right-hand end of the list trustworthy. The app reads the address TRUSTED_PROXY_HOPS entries from the right.

14.1Verifying it end to end

Do this after every proxy change, and before setting ADMIN_ALLOWED_IPS, so you allowlist the address the server really sees. Sign in, copy the site's cookies from your browser (the Supabase auth cookies as well as the activity cookie — the endpoint is behind the same gate as everything else), then:

curl -H "Cookie: <your dashboard cookies>" \
     -H "X-Forwarded-For: 1.2.3.4" \
     https://cbrl.iitkgp.ac.in/api/admin/whoami

The clientIp in the response must be your real address. If it comes back as 1.2.3.4, nginx is forwarding the caller's header unchanged and an allowlist would be trivially bypassed. Fix the proxy configuration before relying on it.

The same endpoint reports whether that address is allowed, whether the allowlist is on, trustedProxyHops, the expected origin, and the raw forwarded headers — enough to diagnose a mismatch from one response.

Setting TRUSTED_PROXY_HOPS wrongly

Too high and the app reads an entry the caller supplied, so anyone can claim an allowlisted address and walk past the allowlist. Too low and it reads nginx's own address, so every user appears to come from the proxy — the allowlist then admits everyone or no one, depending on whether that address is on it. Confirm with /api/admin/whoami rather than assuming.

15Deployment and the committed fallback copy

15.1Deploying an update

git pull
npm ci
npm run build
# restart the process manager, e.g.
sudo systemctl restart cbrl-website

Nothing the dashboard saves lives on the server — content is in site_content and uploads are in the site-media bucket — so a redeploy, even from an old checkout, cannot overwrite editorial work. npm run build prerenders the public pages from the database; it clears Next's persisted fetch cache first so that each build reads the current content rather than whatever an earlier build saw.

Build while the database is reachable

If the build cannot read the database, the pages are prerendered from the committed fallback copy and the build log carries [content] Could not read … warnings. The site then shows that older copy until the next dashboard save of each collection, or the next build. Rebuild once the database is reachable.

15.2Keeping the fallback copy reasonably current

The files under content/ and public/data/ are not updated by the dashboard and drift further from the live content with every save. Nothing depends on them being current, but a fresher copy makes an outage less visible. To refresh one, read the row in the Supabase SQL editor and paste the value into the matching file:

select data from public.site_content where collection = 'members';      -- content/members.json
select raw  from public.site_content where collection = 'publications'; -- public/data/publications.bib

Commit the result like any other change. Never refresh them the other way — running migrate:content against a live project pushes the old copy over the database (section 9.4).

16Deploying elsewhere (Vercel and other hosts)

Because content and uploads are stored in Supabase, the application no longer needs a writable, persistent filesystem for the dashboard to save.

What any host does need:

  • A Node.js runtime able to load Sharp, which the upload route uses.
  • Outbound access to the Supabase project, and to doi.org for DOI imports.
  • Its public address registered as a redirect URL in Supabase Authentication, as https://<host>/admin/auth/callback.
  • The environment variables of section 10. On a host whose proxy chain differs from a single nginx, re-check TRUSTED_PROXY_HOPS with /api/admin/whoami before turning the allowlist on.

If you deploy somewhere only as a preview, leave ADMIN_SESSION_SECRET unset so the dashboard shows its "not configured" screen rather than accepting sign-ins against the live database.

18Backup and restore

18.1What the application keeps for you

Every update to a site_content row first copies the previous version into public.site_content_versions: id, collection, data, raw, saved_at (when that version had been saved) and saved_by (who saved it). The migrations in this repository do not prune the table. This is an "undo" facility inside the same database, not a backup strategy.

18.2Restoring a previous version

In the Supabase SQL editor, find the version you want, then copy it back into site_content:

select id, saved_at, saved_by
  from public.site_content_versions
 where collection = 'members'
 order by saved_at desc
 limit 20;

update public.site_content c
   set data = v.data, raw = v.raw
  from public.site_content_versions v
 where v.id = <id> and c.collection = v.collection;

The restore is itself an update, so the trigger snapshots the version it replaces — a restore can be undone the same way. Because it is run from the SQL editor rather than by an editor, the restored row's updated_by will be empty. The public pages pick it up after the next dashboard save of that collection, or the next build (section 11.4).

18.3A real backup

The content no longer lives on the application server, so backing that server up does not back up the website. Cover, off the machine:

  • The Supabase project's database — in particular site_content, site_content_versions and site_editors. The project also holds CPMS's patient records; treat any database export accordingly.
  • The site-media storage bucket — every image uploaded from the dashboard.
  • .env.local — store this with your secrets, not alongside the content.

content/, public/data/ and public/images/ are in git and need no separate backup.
